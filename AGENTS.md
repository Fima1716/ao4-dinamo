В проекте четыре версии сайта. Клиент выбрал одну.

## 4. Как устроены стили — важно

Файлы стилей подключаются цепочкой:

```
final/style.css  →  variant2-full/style.css  →  variant2/style.css
```

Поверх этой цепочки страница подключает ещё два файла, по порядку: `final/design.css` и `final/sections.css`. Чем позже файл в списке, тем выше его приоритет.

Это значит: **правка в `variant2/style.css` меняет внешний вид сразу трёх версий сайта.**

Поэтому:

- Хочешь поправить секцию основного варианта → ищи её класс в `final/sections.css`.
- Хочешь поправить первый экран → `final/style.css`.
- Правишь базовый `variant2/style.css` → потом открой и посмотри все версии, не сломалось ли.

### Первый экран живёт отдельно

Первый экран (большой заголовок «Новая улыбка за один день» и 3D-протез) сделан в другом стиле, чем остальная страница: другой шрифт, другие цвета.

Чтобы эти два стиля не мешали друг другу, первый экран обёрнут в блок с классом `.v1`.

**Любое правило для первого экрана пиши с префиксом `.v1`:**

```css
/* правильно */
.v1 .hero__h { font-size: 64px; }

/* неправильно — сломает заголовки на всей остальной странице */
.hero__h { font-size: 64px; }
```

## 5. Как вносить правку — по шагам

### Шаг 1. Запусти сайт у себя

```bash
python3 -m http.server 8765
```

Открой в браузере `http://localhost:8765/final/`

### Шаг 2. Найди, что правишь

Текст ищи в `final/index.html` обычным поиском по словам. Внешний вид — в файлах стилей по названию класса.

### Шаг 3. Правь

Делай одну задачу за раз. Не смешивай «поменял текст» и «переделал вёрстку» в одной правке.

### Шаг 4. Проверь глазами

Обязательно посмотри на двух размерах окна:

- **1440 × 900** — компьютер
- **390 × 844** — телефон

Проверь по списку:

- первый экран помещается в окно целиком, ничего не обрезано;
- текст не налезает на картинки и кнопки;
- картинки на месте, ничего не растянуто и не сплющено;
- кнопки «Рассчитать стоимость» открывают окошко с формой, а не прокручивают страницу вниз;
- в поле телефона работает маска `+7 (___) ___-__-__`.

### Шаг 5. Закоммить и выложи

```bash
git add -A
git commit -m "fix(hero): почини отступ у заголовка"
git push
```

**Пуш сам выкладывает сайт на сервер.** Через минуту правка уже у клиента. Отдельно ничего делать не надо.

## 6. Как писать сообщения коммитов

Формат:

```
тип(где): что сделал
```

**Типы:**

| Тип | Когда брать |
|---|---|
| `feat` | добавил новый блок или функцию |
| `fix` | починил поломку |
| `style` | поменял внешний вид: цвета, отступы, шрифты |
| `content` | поменял тексты, цены, фото |
| `refactor` | переписал код, снаружи ничего не изменилось |
| `docs` | правка документации |
| `chore` | служебное: настройки, зависимости |

**Где:** `final`, `hero`, `quiz`, `editor`, `api`, `assets`, `ci`. Если правка общая — можно не указывать.

**Правила:**

- маленькими буквами, без точки в конце, не длиннее 72 символов;
- повелительное наклонение: «добавь», «почини», «убери» — не «добавил» и не «добавляет»;
- по-русски;
- один коммит — одно изменение;
- никаких паролей и ключей в коммите.

**Примеры:**

```
fix(hero): верни пропорции картинки протеза на телефоне
content(team): обнови стаж врачей
style(final): увеличь отступ между блоками
feat(quiz): добавь пятый вопрос про сроки лечения
```

Если нужно объяснить «почему» — добавь абзац после пустой строки. Пиши причину, а не пересказ изменений:

```
fix(hero): верни пропорции картинки протеза на телефоне

Браузер брал высоту из атрибута height, потому что в стилях была
задана только ширина. Добавил height:auto.
```

## 7. Чего делать нельзя

- **Не пушь сломанную вёрстку.** Пуш сразу уходит на боевой сайт, который смотрит клиент.
- **Не клади в репозиторий пароли, ключи, токены.** Никогда и ни в каком виде.
- **Не переделывай структуру блоков без необходимости** — почему, объясню в следующем пункте.
- **Не удаляй старые варианты** (`variant1`, `variant2`, `variant2-full`) — клиент иногда возвращается к ним посмотреть.
- **Не трогай папку `assets/`** без причины: там фотографии реальных пациентов и врачей, заменять их наугад нельзя.

## 8. Редактор текстов на сайте

У клиента есть возможность менять тексты прямо в браузере, без программиста.

Как это работает: к адресу страницы добавляется `?admin`, вводится пароль, после чего любой текст можно нажать и переписать. Пароль спроси у Ефима, в репозитории его нет.

**Что тебе важно знать:**

Правки клиента хранятся не в файлах сайта, а отдельно на сервере. Привязаны они к положению элемента в структуре страницы.

Значит: **если ты переделаешь структуру блока, тексты, которые клиент правил в этом блоке, вернутся к исходным.**

Поэтому перед крупной переделкой вёрстки предупреди Ефима или Илью, чтобы они проверили, не потеряется ли что-то важное.

## 10. Правила для текстов: это медицина

Сайт медицинский, тексты попадают под закон о рекламе. Будь осторожен.

**Нельзя писать:**

- «гарантируем результат»
- «без боли»
- «навсегда», «на всю жизнь»
- «лучшие в Москве» и подобное без подтверждения

**Тире.** В текстах сайта используем короткое тире «–», а не длинное «—»: клиент просил.

**Обязательно должно быть:**

- в подвале: «Имеются противопоказания. Необходима консультация специалиста»;
- у каждой формы: галочка согласия на обработку персональных данных, по умолчанию снята, с ссылкой на политику;
- у цен: пояснение, что входит в пакет.

Фотографии пациентов публикуются с их согласия. Новые кейсы добавляй только после подтверждения от клиники.

## 11. Если что-то пошло не так

**Сайт не обновился после пуша.** Загляни во вкладку Actions на GitHub. Если там красный крестик — открой упавший шаг, там написана причина. Чаще всего это битая ссылка на картинку: проверка специально ловит такое до выкладки.

**Сломал вёрстку и не понимаешь что.** Откатись к прошлому состоянию:

```bash
git log --oneline        # найди нужный коммит
git revert <номер>       # создаст коммит-откат
git push
```

**Что-то неясно про задачу или данные.** Лучше спроси Ефима или Илью, чем выдумай. Особенно это касается цен, имён врачей и медицинских формулировок.
